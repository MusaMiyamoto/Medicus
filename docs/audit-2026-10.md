## A. Executive report

**What Medicus is today.** Medicus is a working prototype of a hardened Debian 13 + XFCE live OS for
Norwegian health personnel. It includes:

- card + PIN login, emergency access and IT mode;
- a patient record and a journal assistant that runs locally (speech → draft note, with a source check);
- Post (messages between institutions), an own browser, an own text editor and a clinical calculator;
- a Helsenorge-style citizen portal and a lawful-request workflow, both against a **simulator** with
  **synthetic** patients only;
- Norwegian and English throughout.

**Evidence.**

- **Tests:** 510 automated tests pass (WSL Debian, Python 3.13, 24 Oct 2026). That is 481 at the start of
  this audit, plus 29 new ones.
- **ISO:** builds reproducibly with `os/build.sh` (about 1.9 GB), with an SBOM for every build.
- **VM tests in this audit period:**
  - the English login screen;
  - wrong-PIN counting;
  - the English session and Calculator;
  - the IT desktop.

**What this audit changed.**

1. **Task Manager (requested):** Medicus' own *Oppgavebehandling* replaces the stock `xfce4-taskmanager`,
   which showed another product's name, had no protected processes and logged nothing.
   - Every stop is confirmed with the IT card PIN through sudo.
   - A root helper checks the protection rules again and refuses a reused PID.
   - It writes stops and refusals to a new hash-chained audit log, which `medicus-revisjon` checks.
2. **Security defect fixed (high):** the local Medicus service (`127.0.0.1:8000`) checked neither the
   `Host` nor the `Origin` header.
   - The session comes from the card in the reader, not from a cookie. So any page open in the
     browser could make the browser open a patient record as the logged-in clinician. That writes a
     false access to the record's access log and notifies the patient.
   - DNS rebinding could read records outright.
   - Fixed and tested. The health network simulator got the same Host check.

**The biggest open items** (details in C and H):

- **Not built:**
  - an installation-to-disk mode with full-disk encryption;
  - real chip cards (PKCS#11) and HelseID;
  - A/B updates with Secure Boot;
  - downtime mode;
  - patient-context sync;
  - snooping detection;
  - pinned dependencies.
- **Not done, needs outside parties:**
  - an external penetration test;
  - a DPIA;
  - a Normen assessment;
  - an MDR classification;
  - a legal review of the lawful-request rules.
- **Blocked on the owner:**
  - the Cloudflare demo on the owner's account;
  - the GitHub ruleset that blocks every merge, even the owner's;
  - publishing the ISO.

**Readiness.** Medicus is ready for **demonstration and a closed technical pilot with synthetic
data**. It is **not ready for real patient data**. That needs real authentication (HelseID and chip
cards), real integrations under agreements, installation with disk encryption, an external
penetration test, a DPIA, and the MDR question settled. See section E.

## C. Missing and inadequate functionality

Ranked by risk to a pilot.

1. **Real authentication** (rows 14, 17): the card reader is simulated, and there is no HelseID or PKCS#11.
   Without these, Medicus can't hold real data.
2. **Installation to disk with full-disk encryption** (row 53): today it is a live system only.
3. ~~**Pinned, hashed dependencies.**~~ Done 24 Oct: a lock file with hashes, checked by the build and CI.
4. **Re-testing on the latest ISO** (rows 15, 16, 19, 40, 43, 46): the code has tests, but the
   end-to-end behaviour has not been seen since these changes.
5. **The Journal assistant's models aren't in the ISO** (row 25): it doesn't work offline out of the box.
6. **Update chain**: no A/B images, no Secure Boot with own keys (row 56).
7. **Downtime mode** (row 58): the most-asked-for safety feature in healthcare IT.
8. **Snooping detection, protected identities** (rows 60, 62): expected by Normen.
9. **Branding leftovers** (row 3): installer and boot loader, and "About" dialogs in remaining XFCE tools.

## D. Technical and security assessment

**Architecture.** It has four layers:

- the card login daemon (`tilgang/authd.py`, its own user, no network);
- a local web service per machine (`medicus/app.py`, FastAPI, 127.0.0.1 only, systemd sandbox);
- national services behind one interface (`helsenett/client.py`; today a simulator);
- native GTK apps (Calculator, Text, Browser, Task Manager).

This is sound for a prototype. The weak point is the single local service, which holds the
unfinished notes and caches in memory (deliberately one worker).

**Checked against the OWASP Top 10 (2021):**

| Risk | Finding |
|---|---|
| A01 Broken access control | **Defect fixed in this audit**: the cross-site and DNS-rebinding hole described in A. Session roles (normal, emergency, IT) are enforced server-side (`normal_session`, `it_session`, `emergency_session`); IT mode gets no patient data (tested). |
| A02 Cryptographic failures | Audit log: SHA-256 chain plus forward-secure HMAC. The TPM key can't be exported. RAM encryption where the CPU supports it. **Open:** no disk encryption, because there is no install mode yet. |
| A03 Injection | No SQL. Subprocess calls use argument lists, not shells. Fødselsnummer (national ID) checksums are validated (`helsenett/fnr.py`). |
| A04 Insecure design | Lawful requests go through a workflow, not access; the threat model is in `docs/pilot.md` §5. |
| A05 Misconfiguration | Hardened sysctl, modprobe blacklists, AppArmor, USBGuard, nftables. **Open:** no Lynis or OpenSCAP report per build. |
| A06/A08 Vulnerable components, integrity | SBOM per build. **Open:** unpinned Python packages (C3), no signed images (C6). |
| A07 Authentication | PIN lockout after three tries, no passwords anywhere. **Open:** the simulated card (C1). |
| A09 Logging | Hash-chained logs for logins, records, USB, Wi-Fi, record systems and now Task Manager stops; auditd for system changes. Logs hold metadata, never patient content. |
| A10 SSRF | The browser and tinyproxy allow only approved hosts; services have `IPAddressDeny=any`. |

**Task Manager (new) design notes:**

- **Least privilege:** only `medicus-it` can start it (`root:medicus-it 0750`). Stopping runs as root
  only through sudo with the IT card PIN; there is no remembered sudo session (`timestamp_timeout=0`).
- **Protection is enforced in the root helper.** It refuses PID 1, kernel threads, all system
  services (uid < 1000), the desktop and itself. Services are restarted with `systemctl` instead.
- **PID reuse:** a process is named by PID *and* start time, so a PID taken over by another program
  is never stopped by mistake.
- **Privacy:** the audit entry holds program name, PID, user and graceful/forced, never the command
  line, which can contain file names with patient names.
- **Patient-work warning:** the browser, record systems and Text warn that unsaved notes may be lost.

**Testing.** 510 unit and integration tests, run on every change. There are no browser end-to-end
tests in CI and no CI at all on GitHub (tests run locally in WSL). Recommended in I.

## E. Legal assessment (engineering reading, not legal advice)

| Area | Where Medicus stands | What a real pilot needs |
|---|---|---|
| **GDPR** art. 9 (health data), 25 (privacy by design), 32 (security), 35 (DPIA) | Synthetic data only. Local processing, data minimisation in logs, no cache of patient data in the browser | A **DPIA** by the data controller (the health trust), records of processing, a data processing agreement if anyone else operates it |
| **Personopplysningsloven** | Follows GDPR | Same; employee monitoring rules apply to staff audit logs (`docs/pilot.md` §7: involve employee representatives) |
| **Helsepersonelloven** §§ 21–25 (confidentiality), § 45 (access to records), § 21a (no snooping) | Reason prompt outside your own list; every access logged and shown to the patient; lawful-request workflow per authority | Legal review of `helsenett/hjemler.py`; snooping detection (row 62) |
| **Pasientjournalloven** § 16–17 (logging and patient's right to see access) | Built against the simulator | Real Helsenorge integration needs an agreement with Norsk helsenett |
| **Pasientjournalforskriften** | Notes signed by the approving clinician (HPR number) | Templates per service; retention rules |
| **Helseregisterloven** | Not relevant: Medicus builds no health register | Confirm with the DPO |
| **"Helsejournalloven"** | No Norwegian act by this name was found. The owner confirmed on 24 Oct that **pasientjournalloven** is meant (row above) | — |
| **Normen** (Code of conduct for information security in the health sector) | Many technical measures match: access control, logging, encryption, network zones | A formal Normen gap analysis |
| **EU MDR 2017/745** and CE | Calculator scores probably class IIa (rule 11); journal assistant at least class I. See `docs/design.md` | Classification with the Norwegian Medical Products Agency (DMP) and a notified body before clinical use. Until then: decision support, sources shown, clinician decides |

## I. Recommendations

1. **Fix the GitHub ruleset first** (J2), so finished work can be merged through pull requests.
2. **Pin dependencies and add CI** (J4): cheap, and it closes a real supply-chain gap.
3. **Do phase 1 before adding features.** Several features are built but not seen working on the
   latest ISO.
4. **Choose the Cloudflare route** (J1). A named tunnel is free but needs a domain on the account;
   Cloudflare Containers needs the paid Workers plan.
5. **Start the legal track early**: DPIA, Normen, MDR. These take longer than the code.
6. **Keep the demo strictly synthetic.** The demo server (`medicus/demo_server.py`) always switches
   demo mode on itself, uses only the simulator, and keeps its data in a temporary folder that is
   removed when it stops. Outside demo mode the demo pages answer 404.
